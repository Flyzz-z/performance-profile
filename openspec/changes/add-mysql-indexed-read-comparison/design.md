## Context

动机与确认范围见 `proposal.md`。当前六场景的只读负载是 sysbench 自带主键查询；`update_no_secondary_index` 是按 `id` 更新 `k`，不能用于索引读对照。`prepare.mjs` 会删除并重建配置的数据库，标准 `k` 分布也不保证单行匹配，因此不能直接拿现有两项结果充当新实验。

已有独立热点实验提供自身编排、原始证据复算、仅合并一个报告字段以及并发修改检查的参考；`protocol.mjs`、`analytics.mjs`、`resources.mjs` 与 `logging.mjs` 可复用。网页在 `site/app.js` 分别渲染独立实验，现有 `/artifacts/mysql/` 路由覆盖结果目录，`conclusions.json` 保留作者手写文本及换行。

该变更同时涉及负载、冻结数据、独立正式验收及可选报告字段，需要设计产物。当前工作区已有结论文案与布局编辑，实施须保留这些编辑。

## Goals / Non-Goals

**Goals:**
- 让两组查询选择性、载荷、参数分布和事件语义一致；以真实表结构及执行计划证明二级索引访问与扫描。
- 将正式实验的数据、脚本、计划、观测、资源与发布验收关联到单一独立结果组，失败时可保留当前报告。
- 使用专属实验数据库及新报告字段，使新增测量可以独立运行、发布和回滚。

**Non-Goals:**
- 不新增范围查询、覆盖索引、主键索引删除、冷缓存或数据规模扫描实验。
- 不重测既有六场景、32 并发、Buffer Pool 或热点实验；不修改其入口的默认矩阵或通用 partial 验收。
- 不把回表查询与全表扫描的差异解释为覆盖索引收益、磁盘物理 I/O 或生产上限；不预填性能比例及作者结论。

## Decisions

### 1. 使用相同数据的两套物理表，真实移除查询二级索引

为每个结果组派生唯一且长度受限的两套数据库名，仅访问自身命名空间，各包含 `sbtest1`–`sbtest10`。先生成一次标准列与载荷，将 `k` 规范为 `id`（1–100,000），保留非唯一单列 `k` 索引；随后复制全部逻辑行到另一套相同表，移除目标 `k` 索引并保留自增主键。源与副本的 `c`、`pad` 等载荷一致；复制与改键均属于准备阶段，不计入正式测量。

每表记录列与索引清单、行数、`COUNT(DISTINCT k)`、键范围及规范化逻辑行摘要。摘要按主键顺序遍历 `id/k/c/pad` 全部数据，分块计算，不只比较总行数或随机种子。冻结后不再准备或写入，两组在结束后重新计算摘要。现有 `sbtest` 不经过通用 reset 入口；已有数据库状态在运行前后留存检查证据。

选择物理删除二级索引而不是 `IGNORE INDEX`，使“无二级索引”与表结构一致。选择 `k=id` 而不是标准随机 `k`，以固定每查询一行的选择性；查询仍只以 `k` 为条件，不利用主键定位。

### 2. 两组共享单一 SELECT 脚本，查询二级索引后需要回表

新增 `benchmarks/mysql/loadgen/scripts/index-read.lua`，每线程建立连接并为十张表准备 `SELECT c FROM sbtestN WHERE k=?`。每事件均匀随机选择表及 `k`，种子 42、按线程派生一致的随机规则，提交一条自动提交查询并消费结果；不是 `COUNT(*)`、批量事件或显式多条 SQL 事务。成功事件必须返回一行，数量异常终止或记为可拒绝发布的错误，不能静默计入吞吐。

使用 `c` 载荷避免覆盖二级索引；`k` 本身虽然无重复，索引定义仍为非唯一，以保持两组逻辑结构仅相差目标索引。相同随机规则意味着相同参数分布和每线程生成规则，不声称不同吞吐下完成的查询总数及实际线程交错完全相同。

通过 Compose 对新增脚本目录只读挂载，使用已有压测端基础镜像，不为增加 Lua 脚本重建镜像。记录 Lua 文件的 SHA-256、SQL 模板、挂载路径与实际参数，并在原始证据验收时核对；正式数据不依赖执行发布时已被修改的脚本。

准备后执行 `ANALYZE TABLE`，对每表首、中、尾与固定种子抽样值保存 `EXPLAIN FORMAT=JSON` 及返回结果校验。有索引组须显示目标 `k` 索引的 `ref` 等值访问，无二级索引组须显示 `ALL`/无访问 key；结束再核验。执行计划中的 `rows` 是估计值，不当成逐查询实测扫描行数。正确性检查和额外执行计划查询在测量窗口外进行。

### 3. 独立编排复用既有协议，不进入六场景默认矩阵

新增 `scripts/index-read.mjs` 和 `scripts/index-read-results.mjs`，增加 `npm run mysql:index-read`。复用现有 sysbench 参数规范、原始输出解析、重复及稳定性算法和 Docker Stats 采样；独立定义两组及六组合，避免把新负载注入旧发布白名单。

CLI 提供 `--dry-run`、`--verification`、`--no-publish`、`--group` 与 `--publish-summary`。dry run 在任何建目录、数据库或服务操作之前返回。验证使用独立命名空间及 `results/verification/<group>/`，短参数或矩阵子集不能获得 formal 身份；正式入口只接受确认的完整协议。

进入前从既有正式报告读取软件与基础镜像身份并对比真实运行环境，核验实际两端配额、3 GiB 缓存、binlog ON 和 1/1/1 日志。压测端镜像维持已有身份，新增脚本另行标识。环境不符直接停止，配置变化不在此变更中自动接受。

记录确定的串行调度顺序：并发 1 先有索引后扫描，并发 8 先扫描后有索引，并发 16 先有索引后扫描；每组合一次 30 秒预热、两次 90 秒，TPS/p99 波动超过 30% 时补第三次。两组冻结数据始终保留，跨组合不改数据或缓存容量。名义净负载时长六组合 × 210 秒至六组合 × 300 秒，即 21–30 分钟；数据准备、核验和进程退出开销另计。

2026-10-13 重测期间，客户端巡检拒绝一次额外连接；独立诊断捕获到每 5 秒健康检查的本地 `mysqladmin Ping` 与短暂未认证连接。原失败窗口仅保存数量，不追认其连接身份或发布该批。用户已确认将容器健康检查改为检查 `/var/run/mysqld/mysqld.sock` 和 PID 存活，不建立 MySQL 连接；`waitForMysql` 在健康状态通过后仍须执行 `SELECT 1`，失败则继续等待。重建服务保留共享卷，先后核验原数据库摘要及正式配置，再启动全新完整结果组。客户端巡检和发布门禁保持原严格条件，不白名单放过未知连接。

沿用独立实验的容器归属和非本次 MySQL 客户端检查，运行串行；出现其他业务或压测负载则本次结果不可发布，不终止其他人的进程。使用明确容器名称及归属证据只清理本次容器，所有采样与子进程受中断控制。结束回读日志/缓存和已有数据库状态，确认本次负载停止。由于协议无需变更日志或 Buffer Pool，原则上仅核验；如果公共工具触碰配置，也必须恢复并验证运行前值。保留自有准备库供追溯，不自动删除共享卷。

### 4. 从原始证据复算后仅合并新实验字段

`indexReadExperiment` 为可选独立字段，结构包含 `schemaVersion`、`purpose`、`runGroup`、`testedAt`、`protocol`、`workload`、`restorationPath` 与 `groups`。两组 id 为 `indexed` / `table-scan`，各有自身环境/数据/计划路径、1/8/16 的 `points`、全部 warmup/measured `runs`、选定汇总值及稳定性。负载证据保存 SQL、脚本摘要及不可覆盖的脚本快照。

验收模块检查同组身份与六组合完整性、实际时长、SQL 与脚本、返回行数正确性、零错误及零重连、计划/数据一致性、重复阈值与是否需要第三次、两端 5 秒采样的 72 秒覆盖/100 秒跨度/10 秒间隔以及结束状态。从原始 sysbench 和资源资料重新推导，不能只信任 `selected` 或 `restorationVerified` 布尔值。

发布遵循热点实验的备份与原子写入方式，额外拒绝已有原始组文件被覆盖及 verification 路径进入正式来源。先保留报告原文，验收后只改变 `indexReadExperiment`，深度比较剩余全部字段；临时写入后检查原报告没有并发变化再重命名。已有同字段若被替换，必须是新完整正式组并有备份；既有主报告元数据和峰值不更新。`--publish-summary` 只做原始证据复核与发布，不再启动负载。

对照表的吞吐倍数由相同并发已选定汇总 QPS 相除得到；分母缺失或非正不计算。p95 沿用直方图近似，p99 沿用 sysbench 输出；QPS/TPS 同为一 SELECT/事件。保留现有每指标的两次均值/三次中位数规则，不挑选最快观测。

### 5. 合并性能看板，保留独立证据归属

用户于 2026-10-13 明确要求把索引读与既有场景放在同一看板，并添加一行索引影响结论。只在 `projectDashboard` 将完整有效的两组正式结果追加为“二级索引点查”和“无二级索引查询（全表扫描）”，使用不同于原六场景的颜色；共同参与筛选、1/8/16 并发选择和四张指标图。`projectReport` 及原始报告保持原结构，索引页峰值仍沿用原场景。32 并发不进入图表，原记录及环境介绍保留。

看板标题说明下显示索引读自身的日期、10 表 × 100,000 行、一查询返回一行与 SQL。统一数值表展示新增两组的吞吐、延迟、CPU 和稳定性，同并发吞吐倍数放在表下；重复记录与环境、数据、执行计划、负载和恢复资料合并到“结果明细”，移除重复的独立图表与控件。缺失或无效索引实验不产生新增曲线或对应结论。

`mysql.index-read` 保留作者手写的新结论，只有有效索引实验存在时才拼接到性能看板原三行结论后。继续采用浅青色结论框、换行与每行冒号前加粗。用户确认的结论为“索引对查询性能影响显著：在 16 并发下，二级索引点查吞吐约为全表扫描的 378 倍。”，比例来自同批正式结果；不自动回写测量结论。

## Risks / Trade-offs

- 两套数据增加了共享 Buffer Pool 中的工作集 → 两组按相同固定 30 秒协议预热并记录资源/波动；本实验量化该确认规模的读查询，不增加冷缓存或容量探测场景。
- `k=id` 为人为控制选择性的数据 → 页面说明每查询一行以及真实 SQL，不声称代表任意业务选择性、范围检索或多行查询。
- 负载耗时可能因长扫描、宿主机休眠而超过窗口 → 保存原始时间和资源覆盖；不完整时长或采样拒绝发布，不能把名义 21–30 分钟当实际承诺。
- 执行计划或查询规则变化可让比较失真 → 发布时核验全部表、负载快照、参数及计划；不使用旧主键点查结果作为索引组。
- 软件或实际配额与旧正式环境不同 → 前置比对后停止，先取得实验条件变更确认，不能自动重跑或放宽匹配。
- 异常中断遗留负载或数据 → 只处理归属明确的自身对象，保存失败记录；无法证明结束状态时保留当前报告。

## Migration Plan

1. 实现独立负载、数据构造、测量、证据验收与可选页面；报告缺字段时页面照常展示现有实验。
2. 先验证 dry run 无副作用以及隔离的短过程验证，覆盖执行计划、查询正确性、重复规则、采样不足、混组、错误、结束失败和原子发布冲突。
3. 在已确认环境与协议下运行六组合正式实验，运行期间保持宿主机/VM 工作且不叠加负载，使用 `--no-publish` 先保留完整正式资料。
4. 对原始资料完整复算验收后原子发布；核对旧报告其他字段完全一致及页面、证据链接和独立指标。实验结论等待作者依据正式结果填写。
5. 回滚时恢复发布备份；原始正式资料保留。回滚网页代码时，可选新字段不会改变既有主看板投影。
