## Context

见proposal.md。当前prepare支持清单前缀并记录真实行数/索引结构；标准oltp_update_index.lua执行单行k更新。主run/collect固定六场景18组合、90秒和重复规则，不适合直接放宽为本次正式协议。资源采样已按期望时长动态验收；页面已有独立Buffer Pool成对指标区。当前工作区另有已确认的读写比例标注及测试改动，必须保留。

## Goals / Non-Goals

**Goals:** 用最少新增代码完成同批次的两个独立结果，锁统计和资源证据能够从原始记录复算，发布时保留原报告其他部分。

**Non-Goals:** 不建立通用实验调度框架；不新增并发、热点规模、异步刷盘或多语句事务；不重新测量现有主测试/缓存实验；不追加验证结果为正式曲线。

## Decisions

### 1. 复用标准脚本，只改变访问ID范围

保留现有10表各100000行，两组各自重新prepare并核验主键和k索引。标准脚本随机选表行为保持一致；分散组运行参数table-size=100000，热点组table-size=1，仅限制更新ID而不改变实际数据量或清单。两组都显式rand-type=uniform，仍每事件一条自动提交UPDATE。记录actualRows=1000000、activeRows=1000000或10及每表ID范围。选择该方式可避免新增Lua、10条/表误变100条热点，以及冷热组表数量不同的混杂；不采用重建成小表的方式。

### 2. 独立入口复用现有底层辅助函数

增加小型独立入口/校验模块，直接复用标准sysbench参数构造、compose调用、prepare、原始解析、Docker Stats及withLoggingRestored；不修改既有正式场景集合、主协议或主collector的拒绝条件。只在该入口构造受约束的运行环境对象来设置访问ID上限，不能修改全局.env默认表规模。dry run只读地列出两组真实数据规模、目标范围及30/60/1协议。

正式和短验证必须明确分开，验证落在verification；唯一正式组和测量标识不可覆盖。资源采样沿用5秒间隔，expectedSeconds=60，即至少48秒覆盖、最大70秒跨度及10秒间隔。提前核验项目容器所有权、8/4实际限额、3 GiB缓存、1/1日志、ARM64与软件一致。采用防闲置休眠保护串行执行；可捕获中断清理本入口拥有的负载和准备容器并回读恢复。旧实例停止状态可由正式入口按原项目配置启动，不能静默修改CPU或日志协议。

### 3. 测量窗口锁计数差分

只读取Innodb_row_lock_waits和Innodb_row_lock_time，保存原值、查询时间和实际窗口长度，在30秒预热结束后取before，正式负载完全结束后取after。不使用Innodb_row_lock_time_avg或最大值，因为它们是全局累计统计而非本次窗口指标。平均每次等待毫秒=deltaTime/deltaWaits，等待速率=deltaWaits/windowSeconds。窗口包含启动/收尾的小量开销，保留实际时间，不强行以60作为计数分母。

计数差分及时间有效性独立测试；禁止其他压测并记录全局计数口径。无需Performance Schema全量事件采样或新增高频轮询。失败数取sysbench的ignoredErrors，reconnects单独保存，不直接采用现有metrics.errors的错误与重连合计值作为失败事务数，也不能用锁等待次数代替。完整、可解析、进程正常结束的非零错误观测如实保留，不挑选为零的重测结果。致命退出或证据不完整则不发布。

### 4. 独立验收与最小原子合并

新结果存入独立summary及报告字段hotUpdateExperiment，两组各保存warmup/measured原始输出、元信息、资源采样和锁before/after。验收从原始输出、采样和数据清单重新计算指标，检查同批次、16并发、30/60/1、各组恰好一个正式观测、SQL与访问范围、实际环境及恢复状态。

发布时读取现有mysql.json，只添加或替换hotUpdateExperiment，其他字段深度相等；已有报告备份在site/data之外，再临时写入并原子替换。缺组或证据错误在写入前拒绝。与主测试共享的只是平台参数，不能把历史主更新结果用作本次分散基线。

### 5. 页面沿用成对指标样式

增加独立全宽区块：TPS、p99、每秒等待次数、平均等待毫秒成对条形图；表格补充p95、等待总次数/累计毫秒、两端CPU和失败数。显示16并发、30秒预热/60秒单次、100万/10条活动记录及本实验日期。逐组详情提供实际限额、日志、索引清单、原始输出、资源和锁证据链接。复用现有低调成对条形图样式，不加入主SCENARIOS或稳定性徽章，不加过程提示横幅。

## Risks / Trade-offs

- [同步刷盘同样影响吞吐] → 两组日志相同，结合锁等待与CPU解释，不把整体差额称作纯锁耗时。
- [热点数据也更容易命中缓存] → 同一百万行真实数据及3 GiB缓存、固定预热，保留环境与访问范围，不声称完全隔离缓存成本。
- [只测一次不能量化重复波动] → 严格执行用户协议，不自动补跑、不评级稳定性。
- [全局锁计数包含其他连接] → 串行压测，采集明确窗口，禁止同项目其他写负载；计数重置或缺失拒绝。
- [10条热点可能不产生预期性能下降] → 保留有效实测，不缩成1条、不增加事务持锁时间或额外正式场景。

## Migration Plan

先通过协议/范围/锁差分/发布隔离单测及页面fixture，短验证保持与正式输出隔离。再执行正式两组、验收并只合并新字段，检查桌面和移动布局及全部资料链接；验收完成后按既有授权归档change。发布失败保持原页面；不删除数据卷或覆盖旧正式证据。
