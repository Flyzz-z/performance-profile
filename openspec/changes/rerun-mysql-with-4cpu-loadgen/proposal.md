# Proposal

## Why

原压测端仅1 CPU，点查32并发吞吐回落无法定位，当前看板还混用了不同日期的结果。用户已确认将4 CPU作为正式压测条件，完整重测已有四场景，最终只发布这一轮。

## What Changes

- sysbench固定4 CPU/1 GiB，MySQL仍为4 CPU/6 GiB、Buffer Pool 3 GiB、ARM64和当前固定镜像。
- 同一结果组串行重测点查、同步索引更新、异步索引更新、读写混合，各测1/8/32并发。
- 保持60秒预热、两次120秒、差异超过10%补第三次的协议。
- 正式测量轻量采样两容器CPU使用及限流计数，作为解释性能曲线的辅助证据，不新增诊断场景。
- 全部12组合成功、证据完整且参数恢复后，整体替换最终报告；不再拼接历史点查/混合。
- 验证与旧数据单独留存，不进入最终页面或当前报告数据；保留正式原始记录追溯。
- 最终页面不展示持久化风险横幅、历史背景参照或批次拼接说明；风险保留在实验README，场景名称、实际参数和测量日期继续展示。
- 用户确认完成必要步骤后，仅替换采样中断的读写混合32并发完整组合；原组合完整隔离保存，其余11组合不变，整组重新校验后发布。

## Capabilities

### New Capabilities

- `mysql-formal-results`: 统一4 CPU压测条件的完整正式运行、资源证据和仅正式数据的发布边界。

### Modified Capabilities

无，已有规格仍在已完成未归档的change中，本次补充正式产出契约。

## Impact

复用成对入口扩展完整正式模式，增加轻量资源采样、正式发布校验与页面辅助信息。更新环境默认值、测试和文档，不改统计公式、业务场景或增加并发档位。
