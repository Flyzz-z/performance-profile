## Context

见proposal.md。当前正式链路为prepare/run/collect及日志恢复入口，报告为4 CPU MySQL、四场景、1/8/32；此前8/2、8/4和16并发诊断资料均独立保存，没有发布。

代码中场景/并发、正式校验、采样器及CPU汇总有4 CPU或1/8/32常量；页面只有四种场景定义，部分资源文案和浏览器断言也固定4 CPU/32并发。prepare当前总是建立标准二级索引，run在一次准备后连续重复，不记录阶段行数。上述位置必须一起调整，不能只改.env或页面。

## Goals / Non-Goals

**Goals:** 复用现有链路完成新的统一正式实验；索引对照只改变索引结构；INSERT增长真实、重复起点可核验；独立缓存实验使用同一数据集比较1/2 GiB并记录页面未命中证据；资源与页面从各实验报告读取正确配额及缓存容量；完整验收后整体替换。

**Non-Goals:** 不增加范围查询、异步无索引更新、异步INSERT、批量INSERT、JOIN、额外冷启动或热点场景；不引入通用配置矩阵、并发锁、调度/恢复框架或监控服务；不改统计公式、不迁移旧原始记录、不将过程验证纳入正式输出；缓存实验不与六场景或历史结果交叉比较。

## Decisions

### 1. 固定本轮声明并复用入口

扩展既有正式场景声明为`point_select/update_index/update_index_async/update_no_secondary_index/insert/read_write`，正式并发为1/8/16，默认MySQL为8 CPU、负载端仍为4 CPU。保留现有ARM64、固定镜像、6/1 GiB内存和3 GiB Buffer Pool。

正式入口生成唯一`formal-8cpu-*`结果组，串行执行18组合。除既有异步更新2/0外，全部为1/1，binlog ON、timeout=1。普通短时或子集仍为verification，不能通过手工改purpose或拼接前次诊断形成正式结果。

准备后必须核验项目容器所有权与实际资源。此前临时验证可能留下Compose配置标签为8 CPU、实际运行限额已恢复4 CPU的状态；不能只依赖标签推断已生效。确认仅为项目容器后可重新应用本轮8 CPU，再回读；外部容器或其他未确认资源不符则失败。不要因此删除数据卷或建设恢复框架。

### 2. 使用已有SQL构成索引结构对照

新增无二级索引场景复用`oltp_update_index.lua`，准备时使用sysbench已有`create_secondary`选项关闭`k`索引。其余场景维持标准结构。实际采集所有十张表的列、主键、自增属性及二级索引，验证同字段、同SQL、同初始规模和相同同步日志策略。

不采用`oltp_update_non_index.lua`，因为它更新`c CHAR(120)`，会混入字段及写入内容差异；也不在计时阶段做DROP/CREATE INDEX。无索引组仍有`id`主键，名称为“无二级索引更新”，不能称作全无索引。

### 3. 单行INSERT复用标准脚本并隔离每次重复

使用`oltp_insert.lua`与`auto_inc=on`；每表主键独立顺序自增，`k`保持二级索引。核验自增字段和SQL模式允许标准脚本的自增行为。新增记录包含标准k/c/pad内容，测的是完整单行新增，不宣称与只改k的UPDATE是纯索引成本对照。

沿用run.mjs测量、解析、补跑和统计流程，对INSERT增加重复前准备步骤：第一次使用入口已经准备的百万行；第二次及必要第三次调用现有prepare重新准备。每次准备采用包含repeat的独立前缀，避免覆盖第一轮清单；对应环境/数据引用随测量切换，保留30秒预热与90秒计时。

预热前核验100万行；预热后、测量前、测量后在计时区间外查询实际行数。预热新增数与该预热成功事件数匹配，正式新增数与测量事件数匹配；每事件一条INSERT。存入逐次记录及汇总。预热会增长，所以正式段起始行数不强行写成100万；页面如实展示起止值。

不使用连续增长后的第二轮直接替代重置，不使用DELETE维持固定行数，也不新建另一套压测引擎。INSERT阶段准备容器与负载容器均须纳入现有可捕获中断清理与日志恢复。

### 4. 按真实配额采样和验收

采样器接收本轮期望MySQL/负载端配额，读取Docker实际NanoCpus和Memory后校验，记录实际limits；使用原5秒Stats采样和CPU累计差分算法。汇总分别按mysql=8、loadgen=4归一化，检查同组配额一致，不再统一除以4。保留72秒最小覆盖、100秒最大跨度、10秒最大间隔和计数有效性门槛。

更新正式校验为六场景、1/8/16、8/4 CPU、既有完整协议和恢复标记；验证原始采样与数据清单，不仅信任汇总valid。无二级索引组要求实际索引为空但主键正确；其余要求标准二级索引。INSERT还验证重复准备引用、独立预热、阶段行数、成功事件增长以及一SQL一事件。失败保持旧报告。

### 5. 整组发布与页面兼容

六场景18组合和独立缓存两组全部验收成功后归档现有报告，按原临时文件替换机制发布包含两部分的新报告，不读取旧组补曲线。缓存结果使用独立实验标识、数据清单和结果集合，不计入18组合校验。旧4 CPU、验证和内部冒烟资料留在站点数据之外。

页面保留四指标看板，新增两种场景及可区分色彩，按报告中真实存在的场景渲染。并发按钮、默认最大并发、场景数和资源单位均取数据，不写死32、四场景或相同4 CPU。新报告显示MySQL 8/负载端4 CPU；实施期旧JSON仍正确显示旧四场景和1/8/32。

环境和逐次结果显示实际索引结构及INSERT阶段行数，初始规模与测量增长分开。保留原始输出、采样链接、日期、错误和稳定性，不恢复风险横幅或历史拼接提示。INSERT数据增长是客观参数，不增加说明性营销区或独立差异面板。

### 6. 独立Buffer Pool容量对比

固定MySQL 8 CPU/6 GiB、sysbench 4 CPU/1 GiB、ARM64、现有镜像、16并发和1/1日志策略，只改变Buffer Pool为1073741824或2147483648字节。两组均固定instances=1、chunk=128 MiB并回读实际值，不能从六场景3 GiB清单继承展示参数。

沿用标准sysbench行结构，初始准备10表各600000行。准备后统计并留存各表主键索引页占用，目标总量1.4–1.6 GiB；可用InnoDB的DATA_LENGTH作为近似分配量，INDEX_LENGTH单独记录，不能把二级索引或ibd文件大小计作主键点查工作集。根据实际占用调整每表行数后冻结同一份数据供两组使用，记录行数、结构、页大小、占用和数据集标识。调参准备属于过程验证，不发布为额外场景。

点查沿用标准脚本，显式设置均匀随机分布及完整每表table-size，访问全部十张表和全ID范围，不能沿用100000上限。两组使用同一冻结数据，不在组间重建或写入。两组独立重启，关闭Buffer Pool dump/load，等待准备活动完成；各预热30秒并保存分段QPS及页面读取速率以核验趋稳，未趋稳则记录现象及重复波动，不自动延长预热，不能将启动阶段混入正式测量。随后各测量两次90秒，QPS或p99差异超过30%补第三次；两次取均值、三次取中位数并保留波动。

在每次测量窗口前后保存Innodb_buffer_pool_read_requests和Innodb_buffer_pool_reads原始计数及时间，差分计算请求数、缺页读取数、缺页读取数/实际窗口秒数和近似页命中率1-reads/read_requests。计数重置、请求增量为零或缺失必须拒绝，不能补成100%命中。命中率是页面请求口径；缺页指Buffer Pool未命中，不是操作系统page fault，reads不能直接证明SSD物理读取。保留两端CPU、实际配额与限流证据，避免预先把全部性能差异归因于缓存。

页面增加独立的两组对比区，展示QPS、p95/p99、页命中率、缺页读取速率及实际数据/环境清单，保留逐次结果和原始链接；不受六场景并发筛选影响，不把两组变成新增主图曲线，不计算与其他实验的差异。实验结束或可捕获失败后恢复并回读原3 GiB Buffer Pool、dump/load及日志配置。数据和缺页指标有效才允许发布，若预期缓存差异未出现，如实保留结果，不挑选数据或未经确认另加正式试验。

## Risks / Trade-offs

- [INSERT自然增长改变测量工作集] → 每次重复从相同百万行准备开始，独立预热，记录真实增长，不声称始终是固定百万行容量。
- [重复准备与预热增加时长] → 测量约64.5-93分钟，准备时间另计；只对INSERT增加必要重复隔离。
- [同步日志开销可能覆盖索引差异] → 保持用户选定的同1/1对照，如实记录，不默认追加异步无索引场景。
- [8/4配额合计超过VM可见10 CPU] → 配额不是独占资源；记录原VM/宿主机清单与两端实际使用，不默认调整VM、不保证线性提速。
- [旧报告被新常量误标] → 页面按报告动态读取，fixture覆盖旧/新报告；正式发布只接受新完整矩阵。
- [中断或无效采样] → 使用防闲置休眠保护并保持质量门槛；现有finally恢复日志，失败不发布；不增加强制终止后的恢复系统。
- [行数估算不等于实际页工作集] → 准备后核验主键页占用并冻结同一数据，随机覆盖全部ID；数据校准资料与正式结果分离。
- [VM文件缓存影响缺页成本] → 使用Buffer Pool窗口计数证明未命中，性能按实测展示，不将页面读取直接解释成SSD I/O。

## Migration Plan

先完成本轮声明、数据准备、INSERT重复隔离、资源及发布校验、缓存实验支持和页面回归。用独立短验证检查两个新增场景的SQL语义、索引、自增、行数增长、8/4采样及缓存计数；校准缓存数据集，任何验证数据不发布。通过后全轮重新运行18组合及独立缓存两组，独立回读日志和缓存配置恢复、核对原始/标准化/汇总/页面一致并整体发布；完成截图、原始链接及最终数据边界验收，保留卷和旧追溯记录。

如实现或运行失败，当前正式JSON保留不动；若已发布发现展示问题，可从保存的旧报告恢复展示，不将验证结果或部分新组合替代整组。旧change不自动归档；本轮完成后再按用户要求同步或归档规格。
